# Inpainter 0.3 — systems

**Inputs and baseline:** Scope is [tasks.md](tasks.md), and the panel is INTERFACE's Assistant. The baseline is Inpainter `dev` at `1cd410f`, whose protocol and host are [0.2's systems](../../history/v0.2/systems.md) with its "As built" section. Members are `host`, `protocol`, `draw`, `client`, `apps/template`, and `apps/simple-sketch`. Everything below is proposed until the owner approves it.

## Boundaries and ownership

- `assistant/` — new library. The conversation, the agent loop, and the OpenRouter client. It depends on `protocol`, `serde`, `serde_json`, and one blocking HTTP client with TLS (`ureq`). It depends on neither `draw`, `eframe`, nor any sub-application. It knows no sub-application, skill, or tool by name: everything it offers the model comes from declarations, at run time.
- `host/` — gains the chat panel, the logo menu, the workspace, and the routing between the assistant and sub-applications. Depends on `assistant` as well. Still on no sub-application.
- `protocol/` — gains the skill messages below.
- `apps/simple-sketch/` — declares its skills and carries out their tools through its session's own operations. For the looking tool it gains a software rasterizer (`tiny-skia`) that draws its document's paint lists to a PNG with no window.
- `apps/template/` — declares one skill, which renames its tab.
- `client/` — `sketch-client` drives every Simple Sketch tool with no host.

There is one conversation per window, and it belongs to that window's workspace. Every request is offered the skills of every running sub-application, so the assistant chooses which application's tools fit the request, as the mission's planning across applications will need. Each tool is offered with a required `tab`, chosen from the open tabs of its sub-application. The context names the selected tab, and an unspecific request means that tab.

**The assistant owns:** the conversation, the chosen model, the request in progress, and the OpenRouter key it reads. **The host owns:** the lock while a request runs, routing each tool call to the sub-application of the tab it targets, the panel's drawing, attachments chosen but not yet sent, the workspace and its file, and the settings: the remembered model choice and the recent workspaces, in `<Inpainter data folder>/settings.json`. **Each sub-application owns** what its tools do, the result each returns, and the undo history of the changes they make. The host and the assistant keep no copy of any document.

## Data and contracts

**From the sub-application:**

- `skills {skills: [{id, name, description, instructions, tools: [{name, description, input}]}]}` — every skill it provides, replacing those sent before. It is sent with the declaration and whenever it changes. `instructions` is plain text telling the assistant how to use the skill well. `input` is a JSON Schema for the tool's input. A sub-application that sends none provides no skills.
- `result {call, ok, output, images?}` — the answer to one `invoke`. `output` is JSON for the model to read: what was found, or what was made and its ids, or, with `ok: false`, why nothing changed. `images` holds any pictures for the model, as PNG data. Any `document`, `tabs`, or other message the call caused is sent before its `result`.

**From the host:**

- `invoke {call, tab, tool, input, group}` — run one tool of a declared skill on that tab. `group` is the request's id. Simple Sketch records every change made under one group, until a change by hand or another group, as one undo step, so one undo removes one request's work.

The protocol stays at version 1: the messages are additions, and a sub-application that does not know them never receives them, because the host invokes only declared tools.

**Between the host and the assistant,** in process, over channels, so the frame never waits:

- The host starts a request with the text, the attachments, the chosen model, the selected tab, and every running sub-application with its name, its open tabs, and its skills.
- The assistant sends back, as they happen: a tool call to route, each reply text, an error, and the request's end. The host answers each tool call with the sub-application's `result`. While a request runs, a newer `skills` declaration replaces the tools offered from the next model turn.
- **The lock,** as the owner set on 2026-10-15. From a request's start to its end, the host draws every sub-application's toolbar, menu rows, and properties panel in their disabled look, and sends no `command`, `gesture`, `select`, or `property` from them, from the canvas, or from shortcuts. Camera changes and tab selection still go through. The host's own controls, and the stop button, stay live. The lock lives entirely in the host, so it works the same for any sub-application.
- A stop ends the loop after the call in progress. A request ends after 40 tool calls at most, with a reply saying so.

**To OpenRouter:** `POST https://openrouter.ai/api/v1/chat/completions` with the conversation, the tools, and the attachments as image parts. The model list is `GET /api/v1/models`, filtered to models whose supported parameters include `tools`. The key is `OPENROUTER_API_KEY` from the environment. It is never written anywhere. Each declared tool is offered as a function named `<application id>__<skill id>__<tool name>`, with the `tab` property added to its input. Attachments are pictures, sent as image parts, and text files, sent as text. Tool results that carry images are passed back as image parts in the following message.

**The system prompt** is fixed text in the `assistant` crate, written generically. It says the assistant works on the person's work in the open tabs, the selected one unless the request says otherwise, only through the tools offered, reads before changing, keeps what the person did, and says plainly what it did and what it could not do. After it come, for each running sub-application, its name, its open tabs, and each skill's name, description, and instructions, from the declaration. Each request begins with a note that the person may have changed the work since the last request, so earlier reads may be stale.

**Simple Sketch's skills** are built from its own hand-action surface, not from a list of shape operations: each tool is carried out by the same session path the hand action takes, so the undo, the document sent to the host, and the save are the ones a hand edit produces. A sketch's contents are its canvases; on each canvas, color layers holding freehand strokes, whose color, opacity, size, dash, and cap belong to the layer's palette color; and objects, which are shapes, text, and groups. The skills cover:

- **Reading:** the canvases and the active one; each canvas's color layers with their palette color, visibility, and lock, and the strokes in each with their ids, bounds, and simplified points; every object in order with its id, kind, name, bounds, transform, properties, and text; the selection; and the visible area in canvas coordinates. Ids are the document's own node, stroke, and color ids.
- **Looking:** a picture of a canvas, or of a region of it, as Simple Sketch's document draws it, returned in `result.images`. This is how the assistant understands a hand-drawn sketch, which the reading tool alone describes only as strokes in boxes.
- **The gestures:** a freehand stroke from points with optional pressure, in a palette color; an erase along a path, which removes ink without destroying strokes; a rectangle, ellipse, or line; text in a box; and moving, scaling, or rotating objects.
- **The commands that change contents:** cut, copy, paste, delete, nudge, group, ungroup, bring forward, send backward, bring to front, send to back, align left, center, and right, rotate, flip, new canvas, and switch canvas. Undo and redo stay with the person, so a request's undo step is never undone from inside it.
- **The properties of contents:** every object, text, and palette-color property the panel edits, including name, color, opacity, size, dash, cap, visibility, lock, canvas padding, corner radius, and text styles.
- **The selection:** select, add to, clear, or replace it, as the select tool's operations do.

Left out, because they are not a sketch's contents or stay with the person: undo and redo; opening, saving, and closing files; recent files; zoom, fit, and the window; the panel; and the drawing tools' own settings, such as smoothing and pressure.

The template's skill renames its one tab. Its tool takes a label and sends `tabs` with it.

## The workspace

As the mission says, the workspace is the host's. As the owner set on 2026-10-15, it is reached from the logo menu, and each window has its own.

**The file** is JSON with the extension `.inpainter`: `{version: 1, tabs: [{app, path?, label, camera?}], selected, conversation}`. `tabs` is the tab strip in order, with the sub-application's id, the file the tab shows, and its camera. `selected` is the selected tab's index. `conversation` is the messages in order: the person's text with the paths of its attachments, the assistant's replies, and the name of each tool it called and whether that call succeeded. A tool's input and output are not kept, because they can hold the work itself, such as a stroke's points or a text's words. Neither are the pictures the assistant looked at. Attachments are kept by path, like the files, and a reopened conversation sends the ones that still exist again. The file holds no work: a sub-application's document never enters it. Until saved, the workspace is named Untitled Workspace. It has unsaved changes when a tab opens or closes, the selection or a camera changes, or the conversation grows. A workspace that holds only the tabs Inpainter starts with, untouched, and an empty conversation has none, so closing it asks nothing.

**From the sub-application:** each entry of `tabs` gains `path?`, the file the tab shows, and `saves`, whether the tab is a document that can be saved to a file. The template's tab does not save; a Simple Sketch tab does. **From the host:** `open {path?}` opens that file in a new tab or, with no path, the tab the sub-application opens of its own at start, such as the template's one tab or a new untitled sketch. `keep {tab}` asks for that tab to have a file: the sub-application runs its own Save, with its own dialog for an untitled document, and answers `kept {tab, path?}`, with no path if the person cancelled. A sub-application started with `--restore` opens no document of its own at start.

**Save Workspace:** for each tab that saves and has no path, the host sends `keep` and waits for `kept`; a cancel cancels the save. A workspace not saved before asks for its file through the host's own file dialog, as does Save Workspace As. Then the host writes the file and adds it to the recent workspaces. **Open Workspace, a recent workspace, and Clear Workspace** first ask "Save this workspace?" when there are unsaved changes, then close every tab through the 0.2 quit flow, so each sub-application asks about its unsaved work. Then each sub-application is started again. To open a workspace, the sub-applications it names, and only those, are started with `--restore`. Each tab is reopened with `open`, with its path when it has one and without one when it has none, and the order, selection, cameras, and conversation are restored. The label comes from the sub-application, as always. To clear, each one is started as at launch, and the conversation empties. A file that no longer exists, or a sub-application that is no longer installed, is left out, and a line in the conversation says which. **New Window** starts another Inpainter process with the same `--app` list and a fresh workspace. **Quit** and the window's close ask "Save this workspace?" when there are unsaved changes, then run the 0.2 quit flow. The question is an `ask` in the existing dialog look, with Save, Discard, and Cancel. During a request, the logo menu's rows other than New Window wait until the request ends or is stopped. The lock covers every sub-application control, including the plus, the tabs' close marks, and the menu's Open.

## Main flow and failures

The person sends "create a circle and a square next to each other". The host starts a request. The assistant calls Simple Sketch's reading tool, and the host sends `invoke` and returns the `result`. The assistant then calls the ellipse and rectangle tools. After each one, Simple Sketch commits a step under the request's group, and sends `document` and `result`. The host draws each document as it arrives, as it does for a gesture. The model's final text becomes the reply.

Failures: no key, a network error, a non-success response, or a model that cannot use tools ends the request with a reply saying so. A tool that fails returns `ok: false`, and the model sees why. If the target sub-application exits or stops responding, the request ends with a reply saying so. The host's 0.2 notice shows as before. The stand-in check that each request's first tool call is a read or a look is a guard against stale positions; the owner's trial of A-3 is the real test. There are no hand edits during a request: the host holds the lock below, so a request's changes are always one undo step.

## Verification seams

These are the mission's tests for the assistant. Each fails on the fake it names.

- **Skill discovery.** A scripted stand-in for OpenRouter records the tools offered in each request. With only the template running, the tools offered are the template's skill exactly; with Simple Sketch and the template, they are both sets exactly. A stand-in registered with Simple Sketch's own id, `simple-sketch`, declares different skills, and the tools offered are exactly the stand-in's. Across all of `assistant/` and `host/`, no declared skill id or tool name appears outside tests. In `assistant/` and the host's new panel and routing files, the words Simple Sketch, sketch, canvas, stroke, shape, circle, and template do not appear either; the carried-over chrome elsewhere in `host/` already names the drawing surface and is not searched for words. Then a fixture sub-application, never named in any source, declares a skill with a made-up tool. When the stand-in calls that tool, the host routes it to the fixture's process and returns its result. This catches an assistant whose knowledge of an app is written into its prompts or code.
- **Coverage.** `sketch-client` reads Simple Sketch's own command list, property list, gesture kinds, and selection operations, and fails if any of them that changes a sketch's contents has no tool. The ones left out are named in the check, so a new command must either gain a tool or be added to that list on purpose. The integration review checks every entry of that list against "Left out" above.
- **The picture matches the screen.** A canvas holding a stroke, a shape, and text is rendered by the looking tool and compared with a capture of the host window showing the same canvas. Text is laid out by egui in the host, so this catches a picture that draws text wrong or leaves it out. This catches skills that cover the examples and not the hand surface.
- **One owner.** With the stand-in scripted to call a making tool, the change appears in Simple Sketch's history: `undo` removes it, and the host holds no copy of the history. The host's display copy only ever comes from `document`. This catches an assistant that works on its own copy.
- **No host.** `sketch-client` sends `invoke` for every Simple Sketch tool with no host and compares each `result`, document, and saved file with an in-process session. This keeps every skill usable through the protocol alone.
- **Without the assistant.** With no key, the 0.2 checks pass unchanged, and a request replies that no key is set. This catches a sub-application that needs the assistant to work.
- **The workspace.** A scripted check saves a workspace with a saved Simple Sketch tab, a Template tab, and a conversation in which the assistant read and drew on the sketch, then reads the file: it holds the sketch's path, and no node id, point, color, or text of the sketch. `sketch-client` then changes and saves that sketch with no host. Reopening the workspace shows the changed sketch and the Template tab, in the same order with the same one selected, and the same conversation. No host code names the template or Simple Sketch to do it. This catches a workspace that keeps its own copy of the work, or one written for one sub-application.
- **The real model.** The owner tries A-1 to A-7 and A-9 with a real model, including a freehand drawing of their own that they ask the assistant to identify and change part of. A stand-in proves the plumbing, not that the skills are good enough for a model to use well.

## As built, 2026-10-15

- **The contract.** The protocol additions are in `protocol/src/skills.rs` and `protocol/src/lib.rs`. The tool's key is `<application id>__<skill id>__<tool name>`, made and split by `tool_key` and `split_tool_key`. The host–assistant interface is the public API of `assistant/src/lib.rs`: `Command`, `Event`, `Request`, `Target`, `Entry`, and `Assistant`. Entries never hold a tool's input or output, so the workspace can keep them as they are.
- **Built in three parts at once,** on 2026-10-15, in worktrees, after the contract: Simple Sketch's skills, the assistant, and the panel with the workspace. They were integrated into `dev` by copying, uncommitted.
- **Simple Sketch's skills** are four skills with 26 tools: `look` (`read_sketch`, `look_at`), `draw`, `edit`, and `style`, in `apps/simple-sketch/src/skills.rs` and `session/assist.rs`. Each restores the person's tool settings and panel page afterwards. The looking picture is drawn in `look.rs` with `tiny-skia`, and text through `draw::text` in an egui context with no window, with its own copy of the Inter fonts. Recoloring part of a freehand drawing is a recipe in the instructions: redraw the strokes in the new color, put that layer on top, then erase the old ink. Ink's color belongs to its layer, and by hand, too, no single stroke can be recolored. The template's skill is `tab`, with one tool, `rename_tab`.
- **The assistant** uses `ureq =3.4.2` and `base64 =0.23.1`. It lists models with `supported_parameters=tools`, and the host's picker keeps only those that also take pictures, because looking needs them. Before each request, earlier requests' tool outputs and pictures are cut to a stub, so later turns don't grow with every read. The conversation the person sees is unchanged. `Command::Note` was added for notices the host makes, such as a file that could not be read.
- **The host:** the first window is 1712 points wide, so the shell keeps the 1280 points it had in 0.2 and Simple Sketch's toolbar still fits. A tab opened after the greeting can declare its `contents` and `panel` then. Reopening a workspace starts a sub-application from the program this window already started for that id, and otherwise from its manifest. The picker's first model, before the person chooses, is the newest Claude Haiku the list offers, which is Claude Haiku 5.5, as the owner chose on 2026-10-15 for cost. The owner's first trial that day showed two failures. The first default, the newest Claude Sonnet, had picked its `:batch` variant, which cannot hold a conversation, so OpenRouter answered 404. A free Qwen model was then rate-limited upstream. Variants such as `:batch` are now never the default. A remembered model that the picker no longer offers gives way to the default. As the owner asked on 2026-10-15, the picker offers a short list of recent, well-known models in the class of Haiku 5.5 and Sonnet 5.5, in this order: Claude Haiku 5.5, Claude Sonnet 5.5, Claude Opus 5.5, GPT-6 Luna, GPT-6.1 Sol, Gemini 3.8 Flash, and Gemini 4 Argon. The list is `PICKER` in `host/src/workspace.rs`. A model OpenRouter stops offering, or one that cannot see pictures, is left out.
- **Checks built:** `host/src/window/checks.rs` runs the real window code against real processes and a scripted OpenRouter. It covers skill discovery with a stand-in application nothing names, the stand-in registered as `simple-sketch`, one owner with one undo, and the workspace round trip. `host/tests/boundaries.rs` searches the host's new files for application words, and all of `host/src` and `assistant/src` for every skill id, tool name, and tool key the built programs declare. The skill id `tab` is left out of that search, being the protocol's own word. `sketch-client` drives every tool and holds the coverage check.
- **Not built:** the comparison of a `look_at` picture with a capture of the host window. The picture was compared by eye only. Some property schemas have no JSON `type`. Claude models accept that, but stricter providers may refuse the tool list.
